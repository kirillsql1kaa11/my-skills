# Оптимизация только через измерения

Когда звучит «медленно», «тормозит», «оптимизируй», «сделай быстрее»:

1. Уяснить, что именно медленно и насколько: какая операция, какой объём данных, какой есть замер от пользователя.
2. Выбрать инструмент замера под стек:
   - Node/JS — `node --cpu-prof`, `console.time` точечно, `hyperfine`/`autocannon` для HTTP;
   - Python — `timeit`, `cProfile`, `py-spy`;
   - .NET — BenchmarkDotNet, `dotnet-trace`;
   - Go — `go test -bench`, `pprof`;
   - БД — `EXPLAIN ANALYZE`, slow query log, статистика плана.
3. Зафиксировать базу: цифра «до». Без неё оптимизацию не начинать.
4. Гипотеза узкого места — из данных замера, не из интуиции. Если данные гипотезу опровергают — признать вслух и пересмотреть.
5. Внести ОДНО целевое изменение, а не пачку разных правок вперемешку.
6. Повторить замер той же методикой и показать «было → стало» цифрами.
7. Если выигрыш < ~10% или усложнение кода больше пользы — честно сказать «это не стоит оптимизации» и предложить альтернативу.
8. Не выдавать прогноз «должно стать быстрее» — только измеренный результат. Если среда не даёт замерить, первым делом предложить наименее трудозатратный способ замера.

Микрооптимизации без измеренной боли допустимы только при почти нулевой стоимости (тривиальная замена, тесты остаются зелёными).
